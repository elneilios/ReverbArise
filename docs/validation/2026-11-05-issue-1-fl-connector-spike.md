## Direct-parameter prototype first

[Disposable device script](issue-1-connector/device_reverbarise_context_probe.py) uses `transport.getLoopMode()` then `plugins.setParamValue(value, paramIndex, mixerTrack, effectSlot, 0)` (`PIM_None`). It targets **only** the hypothetical diagnostic plugin `ReverbArise FL Context Probe`, with two exact parameter names: context and callback acknowledgement. It deliberately cannot target the installed ReverbArise or its saved playback enable. No IPC was implemented.

It scans top-level mixer slots afresh, uses original plugin name rather than user slot label, validates parameter names/count immediately before writes, and sends to every matching instance without saving track/slot identities. Mode is sampled for each target. A 24-bit normalized packet carries a changing sequence and Unknown/Pattern/Song; this avoids treating repeated unchanged values as fresh heartbeats. Ack is intended to change only when the receiver audio callback consumes a packet. FL's return value or immediate parameter readback alone would not prove callback consumption.

`OnInit` sends Unknown; `OnIdle` samples mode; `OnProjectLoad` clears targets and pauses on start/error until LoadOk; `OnDeInit` attempts Unknown. No timer-frequency assumption is made. A receiver **model**, not a VST3 implementation, starts Unknown, ignores duplicate packet numbers for lease renewal, expires to Unknown and keeps user enable/assets separate. It does not serialize context. The model's 100 ms lease is an arbitrary test input, not a proposed host timeout. It deliberately demonstrates why this simple protocol is insufficient for shipping.

## Delivery timing: measured fixture outputs, not FL latencies

Deterministic model: 48 kHz, 256-frame blocks (5.333 ms); previously fresh Song context; next script write at 20 ms. These times were supplied to the model, not measured from a running host.

- Switch to Pattern at 1 ms during playback: callbacks at 5.333, 10.667 and 16 ms still admit Song; first Pattern-consuming block begins at 21.333 ms. **Three incorrect wet-admission callbacks.**
- Switch to Pattern at -1 ms immediately before Play, after a stopped Song sample at -2 ms: callbacks at 0, 5.333, 10.667 and 16 ms admit Song. **Four incorrect callbacks, including the first Play block.**
- At a 100 ms fixture expiry, a repeated packet does not renew validity. The interval before expiry can still leak; too short an expiry can mute valid Song when UI work stalls. Neither an appropriate threshold nor a finite host maximum delay was measured.
- A fast 1,000-block offline loop is rejected because the model unconditionally requires `not offline`. This demonstrates only the chosen mute policy. It does **not** demonstrate heartbeat expiry, missed script updates or a bounce defect; those require a native experiment without that unconditional gate.

The model has instantaneous gating and no wet transition ramp. Production's existing <=5 ms transition can add residual audio after context reaches the callback. Total exposure depends on query age, scan time, host parameter queuing, callback boundary and ramp; there is no established upper bound. A correct mode sample and even a fresh heartbeat do not prove it remains correct at the next callback.

## Setup lifecycle and design recommendation

**Not seamless today.** An opt-in installer could place/update only its owned script folder in the actual configured FL user-data location, retaining edited prior versions. It cannot promise activation. The documented route needs a selected scripting input: in this setup that means a separately provisioned hardware/virtual endpoint or permission to reassign one. No device-free background-script registration was verified. A virtual port is a conditional way to obtain an input, not an inherent requirement of `getLoopMode()` or direct parameter writes; it introduces additional setup/dependency work. No virtual device was installed and no restart requirement for one was tested.

Connection detection needs version negotiation plus **callback-consumed** ACK and recent heartbeat per receiver, distinguishing installed/inactive, discovering, connected Song/Pattern, stale and incompatible. Enumeration or a successful setter call is insufficient. Updates should quiesce/expire context, check protocol compatibility and use documented reload/reselection; removal should detach the dedicated assignment before deleting only owned files. Do not silently edit another controller's script, combine scripts, change global MIDI configuration, or trust DeInit as removal confirmation. None of installation/activation/update/removal was executed here.

The prototype's full scan can inspect up to 512 tracks × 10 slots each idle invocation, and each target adds several calls. It is deliberately simple and not suitable for UI-thread rollout. A production design needs measured discovery budgets, dirty-event-assisted rescans, bounded periodic reconciliation, all-instance refresh latency and visible overload behavior. User slot renames should not change protocol identity. Nested Patcher effects are not covered by this top-level scanner. Duplicates, project switches and multiple FL processes require fresh runtime ownership; do not reuse durable project/swell identities as connector tokens.

If an isolated direct-route host experiment becomes possible, use a separately named diagnostic VST3 with stable probe parameter IDs and **runtime challenge-bound** messages/ACKs. Verify FL can enumerate/control the endpoint even if non-automatable, that repeated heartbeats arrive, and that restore/automation cannot forge connection or mark the project dirty repeatedly. A nonce must be verified by the receiving runtime, not merely read before an index-based write. Prove FL's slot mutation serialization or use an addressed receiver protocol; checks before writes alone cannot prove safety.

Only if that route cannot provide those properties should a worker-side IPC prototype be considered: per-FL-process/project-epoch/runtime-instance handshake, versioned bounded messages, no persisted connection identity, reject old sessions and disconnect to Unknown. IPC can avoid writing a replacement slot or replaying an automation parameter, but still needs the FL script activated and cannot ensure mode delivery before audio. No IPC is recommended as a latency cure.

For any later approved design, host context must remain **transient** and independent of saved user playback enable. Song context must never enable playback the user disabled. Pattern may inhibit **Perform scheduled wet only**, restoring dry even with saved Wet Only routing through the existing bounded transitions; Learn Pattern capture, Export/manual preview, accepted source/renders and persistent identities retain their contracts. Define Unknown behavior explicitly for the opt-in connector policy rather than silently changing all existing projects. Callback work would consume a bounded atomic snapshot/sequence, validate freshness and apply a gate; discovery, IPC, formatting and storage stay off the callback. This Python model provides no native realtime-safety proof.

**Offline remains a review blocker:** runtime restore begins Unknown; old Song state cannot authorize bounce. A snapshot from a previous realtime heartbeat may already be stale when bounce begins, and expiry during fast rendering can omit valid wet. Require an explicit reviewed operation-scoped policy and matching audio tests; do not use offline mode as proof of Song or change the #73 path in this spike. Until activation, addressing, restoration and offline behavior are verified, retain the manual fallback and describe a connector only as a possible optional context aid.
